\section{Objective}

This project implements an interactive pipeline hazard simulation applet for a single-issue, in-order processor model. The applet allows a user to enter a short sequence of assembly-like instructions, select a 4-stage or 5-stage pipeline, optionally enable data forwarding, and observe the pipeline schedule cycle by cycle.

The focus of the simulator is RAW (Read After Write) data hazards. The simulator does not model branch prediction, control hazards, structural hazards, caches, exceptions, interrupts, out-of-order execution, superscalar issue, or multi-cycle functional units.

\section{How to Run the Applet}

The submission is a static web app. To run it, open \texttt{index.html} in a browser from the project folder. The main source files are:

\begin{itemize}[leftmargin=*]
    \item \texttt{index.html}: Defines the app layout and controls.
    \item \texttt{style.css}: Defines the visual design, sticky instruction pane, pipeline table styling, tooltips, and forwarding arrows.
    \item \texttt{pipeline.js}: Contains the parser, pipeline timing model, RAW hazard detection, stall insertion, and forwarding event generation.
    \item \texttt{ui.js}: Connects the simulator state to the browser UI, including stepping, auto-run, reset, hazard logs, forwarding logs, tooltips, and table rendering.
\end{itemize}

\section{Instruction Input}

The applet accepts at most 10 non-empty instructions per simulation. Instructions are entered one per line in the input box. If any line cannot be parsed, the full input is rejected and no partial program is ingested. The error log reports the original line number and the reason the line failed to parse.

The accepted instruction formats are:

\begin{center}
\begin{tabular}{ll}
\toprule
Instruction type & Format \\
\midrule
Arithmetic register & \texttt{ADD rd, rs, rt} \\
Arithmetic register & \texttt{SUB rd, rs, rt} \\
Arithmetic register & \texttt{AND rd, rs, rt} \\
Arithmetic register & \texttt{OR rd, rs, rt} \\
Immediate arithmetic & \texttt{ADDI rt, rs, imm} \\
Immediate arithmetic & \texttt{ORI rt, rs, imm} \\
Load & \texttt{LW rt, offset(base)} \\
Store & \texttt{SW rt, offset(base)} \\
\bottomrule
\end{tabular}
\end{center}

Registers must use the form \texttt{R<number>}, for example \texttt{R1}, \texttt{R2}, or \texttt{R10}. Immediates and memory offsets must be integers. The supported instruction set includes \texttt{ADD}, \texttt{SUB}, \texttt{LW}, \texttt{SW}, \texttt{AND}, \texttt{OR}, \texttt{ADDI}, and \texttt{ORI}.

\section{Pipeline Configurations}

The applet supports two pipeline models:

\begin{itemize}[leftmargin=*]
    \item \textbf{5-stage pipeline}: \texttt{IF}, \texttt{ID}, \texttt{EX}, \texttt{MEM}, \texttt{WB}.
    \item \textbf{4-stage pipeline}: \texttt{IF}, \texttt{ID}, \texttt{EX}, \texttt{MEM/WB}. In this model, memory access and write-back are represented as one combined completion stage.
\end{itemize}

The selected pipeline changes the produced schedule. In the 4-stage pipeline, instructions complete earlier because \texttt{MEM} and \texttt{WB} are combined into \texttt{MEM/WB}.

\section{Explicit Timing Assumptions}

The simulator uses the following timing assumptions throughout the hazard detector, schedule builder, and forwarding visualizer. These assumptions determine whether a RAW dependency requires stalls or can be satisfied by forwarding.

\begin{itemize}[leftmargin=*]
    \item The processor is single-issue and in-order. At most one new instruction is fetched per cycle, and instructions are not reordered.
    \item Each pipeline stage takes one cycle. Memory access completes in the memory stage; the simulator does not add cache misses, variable memory latency, or structural conflicts.
    \item The \texttt{ID} stage performs instruction decode and register read. For \texttt{LW} and \texttt{SW}, the memory offset and base register are decoded in \texttt{ID}; the effective memory address is calculated in \texttt{EX}.
    \item In the 5-stage pipeline, an ALU instruction has stages \texttt{IF}, \texttt{ID}, \texttt{EX}, \texttt{MEM}, and \texttt{WB}. The architectural register file is updated in \texttt{WB}.
    \item In the 4-stage pipeline, the final completion stage is \texttt{MEM/WB}. This stage represents both memory access, where needed, and register write-back.
    \item When data forwarding is disabled, the simulator assumes there is no bypass path. A consumer cannot use a producer's register result until the cycle after the producer reaches \texttt{WB} in the 5-stage pipeline, or the cycle after the producer reaches \texttt{MEM/WB} in the 4-stage pipeline.
    \item When data forwarding is enabled, ALU results may be bypassed from the producer's \texttt{EX/MEM} pipeline register to a later consumer \texttt{EX} input. If the consumer is farther away, the same value may be forwarded from the later \texttt{MEM/WB} path.
    \item Load data is not available at the end of \texttt{EX}; it is available only after the load's memory stage. Therefore, an immediately dependent load-use instruction still stalls once before receiving the value through the \texttt{MEM/WB} forwarding path.
    \item A store has two source uses. The base register is needed for address calculation in \texttt{EX}. The numeric offset is an immediate value decoded in \texttt{ID}, so it is not a RAW dependency. The store-data register is consumed in the memory stage, so a producer may forward the data value to the store's \texttt{MEM} stage in the 5-stage pipeline or to \texttt{MEM/WB} in the 4-stage pipeline.
    \item If forwarding is enabled and a producer reaches \texttt{WB} or \texttt{MEM/WB} in the same cycle that a consumer is in \texttt{ID}, the value is treated as visible through the register file read, so the simulator does not draw a redundant forwarding arrow.
    \item If multiple earlier instructions write the same register, the simulator uses the latest earlier writer only. This prevents an instruction from incorrectly reading a stale value from an older producer.
\end{itemize}

\subsection*{Correctness Rationale}

Correctness is demonstrated by applying the same availability rule to every source operand before an instruction is scheduled. For each source register, the simulator finds the nearest previous instruction that writes that register. If the selected model says the value is unavailable at the source's required stage, the consumer is delayed and the table shows explicit \texttt{ST} stall cells. If forwarding is enabled and the value is available through a valid bypass path, the simulator records the forwarding event and draws the arrow from the producing stage to the consuming stage. Thus, every visible stall or arrow corresponds to one RAW dependency under the assumptions above.

\section{Pipeline Visualization and Interaction}

The applet is used from left to right. The left sidebar defines the simulation input, while the right side explains the schedule, data forwarding behavior, and hazards produced by that input.

\subsection*{Left Sidebar Workflow}

\begin{enumerate}[leftmargin=*]
    \item Select the pipeline type: either the 5-stage model with \texttt{IF}, \texttt{ID}, \texttt{EX}, \texttt{MEM}, and \texttt{WB}, or the 4-stage model with \texttt{IF}, \texttt{ID}, \texttt{EX}, and combined \texttt{MEM/WB}.
    \item Enable or disable data forwarding before loading or running the program. The status label beside the checkbox shows the active forwarding mode.
    \item Enter instructions manually or choose a preset test case from the dropdown. The accepted syntax is shown by hovering over the information icon in the instruction box.
    \item Click \textbf{Load} to parse the program and build the schedule. If any instruction is invalid, the program is rejected and the Detected Hazards card reports the failing line.
    \item Use \textbf{Step} to advance one cycle at a time, or \textbf{Auto-Run} to animate the schedule until completion.
    \item Use \textbf{Reset Run} to return the loaded program to cycle 0, or \textbf{Clear} to remove the program and reset the interface.
\end{enumerate}

\screenshotfigure[0.5\textwidth]{images/Left_sidebar.png}{Left sidebar controls.}

\subsection*{Reading the Output Cards}

The Pipeline Visualization card displays instructions as rows and cycles as columns. Each populated cell shows the stage occupied by that instruction during that cycle. Empty cells indicate that the instruction has not yet started or has already completed. The instruction column remains visible while horizontally scrolling through cycles, and the table grows only as cycles are rendered during step execution or auto-run.

The Data Forwarding card shows whether forwarding is enabled or disabled, states the active forwarding rule, and lists forwarding transfers once they become visible. When forwarding is enabled, arrows in the pipeline table connect the source stage to the consumer stage; hovering over an arrow identifies the register and the source/destination stages.

The Detected Hazards card lists parse errors before a program is loaded and visible RAW hazards during execution. Stall cells in the pipeline table also show the blocked register, and hovering over a stall cell gives a more detailed reason.

\section{Hazard Detection}

The simulator detects RAW hazards. For each instruction, the simulator checks the latest prior instruction that writes each source register. If a source register depends on an earlier result that is not yet available under the selected model, the consumer instruction is delayed by inserting explicit \texttt{ST} stall cells.

With forwarding disabled, the result availability rule is conservative: an instruction that needs a register written by an older instruction must wait until after the older instruction has completed \texttt{WB} in the 5-stage pipeline, or after \texttt{MEM/WB} in the 4-stage pipeline. This is why back-to-back dependent ALU instructions produce visible stalls when forwarding is turned off.

WAR and WAW hazards are not modeled as baseline hazards because the simulator is single-issue and in-order. Control and structural hazards are not simulated.

When a stall appears, the visible cell says which register is being waited on, for example \texttt{Waiting for R1}. Hovering over the stall gives a more detailed explanation, such as which instruction is expected to produce that register value.

\section{Forwarding Model}

When forwarding is enabled, the simulator generates forwarding events for RAW dependencies that can be satisfied through bypassing. The UI highlights the source and target cells and draws a forwarding arrow. Hovering over an arrow shows which register is being forwarded and the source and destination stages.

The forwarding model assumes a standard in-order MIPS-style datapath:

\begin{itemize}[leftmargin=*]
    \item ALU results are produced by \texttt{EX} and may be forwarded through the \texttt{EX/MEM} path to a later \texttt{EX} input.
    \item If an ALU result is needed after the producer has moved past \texttt{MEM}, the simulator represents the bypass as a \texttt{MEM/WB} path to the consumer's required stage.
    \item Load data is available only after the load's memory stage, so a direct load-use dependency still requires one stall before forwarding from \texttt{MEM/WB} to the consumer's \texttt{EX} stage.
    \item For loads and stores, \texttt{ID} reads the base register and decodes the immediate offset. The effective address is calculated in \texttt{EX}, so a RAW dependency on the base register must be resolved before the address-calculation \texttt{EX} stage.
    \item Store data is consumed in the memory stage, so store-data dependencies can forward to \texttt{MEM} in the 5-stage pipeline, or to the combined \texttt{MEM/WB} stage in the 4-stage pipeline.
    \item If a producer reaches \texttt{WB} or \texttt{MEM/WB} in the same cycle that a consumer is in \texttt{ID}, the value is treated as readable from the register file, so no unnecessary forwarding arrow is drawn for that case.
    \item If multiple earlier instructions write the same register, the simulator uses the latest prior writer for the dependency, avoiding stale forwarding.
\end{itemize}

\section{Implementation Structure}

\subsection{\texttt{pipeline.js}}

\texttt{pipeline.js} contains the core simulation logic. It defines:

\begin{itemize}[leftmargin=*]
    \item \texttt{Instruction}: stores parsed instruction fields, source registers, destination register, schedule, visible stages, timing, and stall reasons.
    \item \texttt{PipelineSimulator}: stores the loaded instructions, current cycle, pipeline type, forwarding mode, hazards, forwarding events, and parse errors.
\end{itemize}

Important methods include:

\begin{itemize}[leftmargin=*]
    \item \texttt{loadInstructions}: validates all input lines before accepting the program.
    \item \texttt{parseInstruction}: parses and validates supported instruction syntax.
    \item \texttt{getLatestRawDependencies}: finds the most recent prior writer for each source register.
    \item \texttt{buildSchedule}: computes instruction timing, stalls, hazard messages, and forwarding events.
    \item \texttt{createSchedule}: converts timing into the visible cycle-by-cycle stage row.
    \item \texttt{step}, \texttt{runToEnd}, and \texttt{resetRun}: control visible simulation progress.
\end{itemize}

\subsection{\texttt{ui.js}}

\texttt{ui.js} renders the simulator state. It builds the table headers and cells for visible cycles only, renders hazard and forwarding logs, draws forwarding arrows, manages the sticky instruction shield, and implements auto-run as a 600 ms cycle-by-cycle loop.

\subsection{\texttt{style.css}}

\texttt{style.css} handles the visual presentation. It defines the dark interface, stage cell colors, stall styling, forwarding highlights, sticky instruction pane, forwarding arrow overlay, and responsive behavior.

\section{Limitations}

The simulator intentionally focuses on simple in-order RAW hazard behavior. It does not simulate:

\begin{itemize}[leftmargin=*]
    \item branch or jump instructions,
    \item control hazards,
    \item structural hazards,
    \item caches or memory latency,
    \item exceptions or interrupts,
    \item out-of-order execution,
    \item superscalar issue,
    \item multi-cycle functional units.
\end{itemize}

The applet is designed to make the behavior of simple in-order pipeline RAW hazards clear and visible rather than to reproduce every feature of a real processor.

\section{Conclusion}

The applet provides a compact interactive pipeline hazard simulator. It supports user-defined instruction sequences, 4-stage and 5-stage pipeline configurations, cycle-by-cycle visualization, step and auto-run execution, reset behavior, RAW hazard detection, stall insertion, and forwarding visualization. The code is organized so that the simulation logic remains in \texttt{pipeline.js}, while rendering and interaction behavior are handled separately in \texttt{ui.js} and \texttt{style.css}.
